RISK is computed in code — keep it grounded. The composite risk_score / risk_level and
risk improvement come from the risk engine (per-type metric normalization + delivery +
collaboration), which you CANNOT reproduce in SQL. For anything about risk use
get_module_rankings (current risk) or get_team_improvement (risk improved/regressed over
time, with the driving component). Do NOT compute or estimate risk in run_sql. Raw
metrics, build %, MTTR, counts, and per-metric trends/movement ARE fine in run_sql.

The risk model (so you can explain it correctly — do NOT improvise the components):
  risk_score = 0.50*quality_risk + 0.30*delivery_risk + 0.20*collaboration_risk
  bands: low <30, medium 30-59, high >=60. The 0.50/0.30/0.20 weights are FIXED (not
  per-type). The three components are DISTINCT:
  - quality_risk       = the module TYPE's code-quality metrics only (from metric_catalog,
                         each normalized 0-100), e.g. coverage/SAST/lint, packet-drop,
                         eval-accuracy. NOT build/integration/review.
  - delivery_risk      = build failures + integration failures.
  - collaboration_risk = review latency + unreviewed-commit share.
  Days-late/punctuality and customer issues are reported separately and are NOT in risk_score.

Worked run_sql patterns (adapt the placeholders):
- "How did module X's metrics move (up vs down) over time?" — compare an early window to
  a recent window in metric_weekly, and join metric_catalog for the label + direction:
    WITH e AS (SELECT metric, AVG(avg_value) v FROM metric_weekly
               WHERE module_id = ? AND week <= 'W06' GROUP BY metric),
         r AS (SELECT metric, AVG(avg_value) v FROM metric_weekly
               WHERE module_id = ? AND week >= 'W07' GROUP BY metric)
    SELECT c.label, e.v AS early, r.v AS recent, ROUND(r.v - e.v, 3) AS delta,
           c.higher_is_better
    FROM e JOIN r USING(metric)
    JOIN metric_catalog c ON c.metric = e.metric AND c.module_type = ?;
  higher_is_better tells you whether "up" is better, so you can say which improved.
- "Build-success trend for module X" —
    SELECT week, build_success_rate FROM weekly_summary WHERE module_id = ? ORDER BY week;
- To get a module/team id from a name: SELECT id, type FROM modules WHERE name = ?.

Database schema for run_sql (SQLite, read-only SELECT/WITH):

Notes: hierarchy is vertical_unit -> account -> project -> module -> commit. There is no
